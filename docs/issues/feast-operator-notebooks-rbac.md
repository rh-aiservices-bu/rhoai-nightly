# feast-operator-controller-manager CrashLoopBackOff on 3.5.0: Notebook ConfigMap controller lacks RBAC for notebooks.kubeflow.org (granted to the wrong ClusterRole)

**Jira: NOT FILED** — filing target: RHOAIENG, component Feast/FeatureStore. This file is the ready-to-file draft.

## Summary

On `rhods-operator.3.5.0` (GA-track nightly, verified on a clean 2026-07-30
install), `feast-operator-controller-manager` CrashLoopBackOffs at startup.
Its new Notebook ConfigMap controller watches `notebooks.kubeflow.org`
cluster-wide, but the ServiceAccount has no RBAC for it. Startup log:

```
INFO setup Unable to validate Notebook CRD (insufficient permissions), will attempt setup
      {"CRD": "notebooks.kubeflow.org", "GVK": "kubeflow.org/v1, Kind=Notebook"}
INFO setup Notebook ConfigMap controller setup completed successfully
...
ERROR failed to wait for notebook caches to sync kind source: *v1.FeatureStore /
      *v1.ConfigMap: timed out waiting for cache to be synced
ERROR setup problem running manager
```

The controller detects the missing permission, proceeds anyway, the notebook
cache group can never sync, and the whole manager exits (~2 min per attempt).
`DataScienceCluster` FeastOperator health degrades accordingly.

## The precise RBAC misplacement (live-verified on 3.5.0)

```
feast-operator-manager-role        (binds SA feast-operator-controller-manager, the crashing pod):
    apiservers.config.openshift.io: GRANTED   (RHOAIENG-79331 fix — present)
    notebooks.kubeflow.org:         MISSING   <-- the bug

opendatahub-feast-manager-role     (binds the opendatahub-feast-operator SA):
    notebooks.kubeflow.org:         GRANTED   <-- rule exists, wrong role
```

i.e. the notebooks grant was added to the meta-operator's role instead of the
controller-manager's role that actually runs the Notebook ConfigMap controller.

**Where the drop happens (source-verified 2026-07-31):** the feast upstream
manifests DO contain the notebooks rule — rhoai-3.5-ea.2's vendored
`prefetched-manifests/feastoperator/rbac/role.yaml:131-138` has it and renders
into `feast-operator-manager-role`. On rhoai-3.5, however, the
controller-manager's ClusterRole is generated by the
`odh-feast-module-operator` wrapper image (the role no longer appears in any
vendored manifest), and the wrapper's rendering **omits the notebooks rule** —
the live 3.5.0 cluster role lacks it while `opendatahub-feast-manager-role`
(from `prefetched-charts/feastoperator/templates/...clusterrole.yaml`) keeps
it. So the bug is in the odh-feast-module-operator's RBAC generation, not the
feast manifests themselves.

## Reproduce

Clean 3.5.0 install with FeastOperator managed → observe the crashloop and
`oc auth can-i list notebooks.kubeflow.org
--as=system:serviceaccount:redhat-ods-applications:feast-operator-controller-manager -A`
→ `no`.

## Fix

Add `kubeflow.org / notebooks / get,list,watch` to
`feast-operator-manager-role` (or whatever the CSV generates for the
controller-manager SA).

## Workaround (ours, verified)

Supplementary ClusterRole+Binding granting the SA notebooks get/list/watch —
pod goes 1/1 Running with 0 restarts immediately after. (Additive RBAC; does
not fight the operator's reconcile.)

Related: RHOAIENG-79331 (the apiservers.config.openshift.io sibling, Closed for
3.5 GA — same operator, same failure mode, different resource).
